# 航次、停机状态与详情布局（2026-09-30）

2026-10-09 当前策略：按 600 秒周期分散目标，飞机基础位置合并批量获取，同一周期共享原始响应（最长 600 秒）；航班详情和近期记录逐架分散查询。所有 FR24 请求共用 3 秒间隔，429 根据 Retry-After 与 60～900 秒递增退避暂停。每次实际请求只尝试一次；未请求的延后不会写虚假原始证据。页面每 15 秒读取本地记录，不触发供应商采集。已有规则历史中的 min_poll_seconds 保留为历史证据，运行代码不读取它。

## 已核实的来源字段

- MarineTraffic position：timestamp、lat/lon、hasNewerSatellitePosition、speed、course、draught。2026-09-30 实测 COSCO SHIPPING UNIVERSE 返回更新的卫星船位标记，公开坐标仍是旧时间。这个标记不能证明离岸距离；界面写“岸基未更新 · 有卫星船位”。不请求任何受限卫星坐标。
- 用户 SDK 的 general/voyage/info 方法已经可用。项目仍保留固定版本的位置 SDK，补充调用集中在 marine_details.py，使用同样的公开端点，并保留响应字节及身份校验。general.subtype 明确返回 Container Ship；不会使用 AIS Cargo 大类猜细分船型。
- voyage 的 departurePortId/arrivalPortId 与 info.values.last_port_id/next_port_id 一致后，才采用港口名称及 UN/LOCODE。两艘船实测分别是 HAMBURG → SINGAPORE 和 SINGAPORE → ROTTERDAM。航次时间按 ATD/ATA/ETD/ETA 区分，页面统一显示 JST。
- FR24 注册号 feed 缺失时读取公开 flight/list.json（fetchBy=reg，最多 10 条）。端点已在官方网页脚本和两架现有飞机的真实响应中核实。按注册号及已配置 ICAO24 校验；在有效记录中优先进行中航班，其次近期待飞航班，再展示最近完成航班。实际到达或明确 landed 才显示已降落。estimated arrival 本身不能证明未起飞。若历史接口失败，会核查已知的最近 flight ID；不从“坐标消失”推断落地。
- [FR24 注册号页面](https://www.flightradar24.com/data/aircraft/ja602f)提供最近航班的起降时刻。接口未分配下一航班时，只能展示最近航班，不能保证获取到未来计划。

## 数据与界面边界

新增 monitor_context 表，保存最近一次通过身份及格式校验的响应、核查时间和 raw_id。它与用于风险评估的 latest 独立：过期船位可以附带新鲜航次和卫星提示；无坐标的航班历史可以提供已降落/未起飞状态。这些情况不把历史坐标改成实时、不生成新的位置风险事件，也不覆盖既有评估与历史。原始响应仍逐次保留。

特殊状态只有在最近一次采集成功、上下文仍在有效窗口内时显示。失败或过期后回到普通数据健康提示。飞机的“最近航班已降落”说明具体航班，不断言飞机当前物理位置。无实时坐标时不重新进行飞机位置/航班风险评估，详情与地图中的历史位置有明确标识。

详情采用状态与航线卡、起降/离到港时间表、资产资料及最近位置分组。船舶增加船旗、长宽、呼号、航速、航向、吃水；只有已返回的字段才展示值，缺失明确标示。原始记录及管理项留在详情下部。

## 验证

tests/fixtures 中的字段来自本轮实际响应，测试按当前时间平移时间戳以检查稳定的状态转换。覆盖卫星标记与过期坐标并存、恢复岸基定位、身份错配与港口错配、接口失败、落地后待飞、历史数据过旧、未来实际时间、状态歧义，以及重复手动采集实际发起请求且不重复生成风险事件。

本地预览使用采集样本回放；正式数据与自动采集设置以服务器部署后的验证为准。
